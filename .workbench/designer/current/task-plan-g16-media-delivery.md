# G16 — Private media delivery: Design Note + Task Plan
**Gate:** `docs/SECURITY.md` G16 — "Cloudinary URLs are public if guessed; move `snapshot_media` (and form-check clips) to signed/authenticated delivery."
**Written:** 2026-09-15 · **Status:** CONFIRMED (designer, 2026-09-16) — Option A, window accepted. **Tasks 1–3 built 2026-09-16.** Cloudinary is not yet configured in production, so there are no assets to migrate: task 4 (rename script) is deferred until there are; tasks 5–6 open (6 partly done: CHANGELOG / SECURITY / DEFERRED updated).

## What is actually exposed today (verified in code)

- Client media — progress photos (`snapshot_media`) and form-check clips (`session_exercise_media`) — is uploaded with Cloudinary's default delivery type **`upload`**: anyone holding the URL can fetch it, forever, with no credential. `cloudinary.service.ts` `uploadBuffer()` sets no `type`.
- The URL is stored whole in `cloudinary_url` and returned as-is by both serializers (`snapshot-media.ts:52`, `session-exercise-media.ts:47`); the frontend puts it straight into `<img src>` / `<video src>` (`progress-photos/*`, `SessionHistoryPanel`, `MediaPlaybackModal`). `cloudinary_public_id` is stored alongside.
- Public ids are Cloudinary-random under UUID folders (`trainer-app/clients/<clientId>/snapshots/<snapshotId>/<random>`), so **"guessed" is not the realistic path** — a URL has to *leak*: shared screenshot of a devtools panel, a browser history sync, a report forwarded, a device the athlete no longer controls (the service worker keeps `res.cloudinary.com` responses CacheFirst for 30 days), or the Cloudinary console/API key.
- Exercise library media (`exercise_media`) is public by design and stays public — it is the shared library. The frontend's `getThumbnailUrl()` string-rewrite (`components/exercises/utils.ts`) is used **only** for exercise media; nothing rewrites a client-media URL, which matters below.
- The monthly report email does not embed photos (`report.service.ts` reads no media). Export (`GET /auth/export`) includes media rows with their URLs.
- `/privacy` promises progress photos are private to the trainer/athlete. Today that is true only as long as no URL has ever left the app.

**Threat model, ranked:** (1) a leaked URL keeps working forever; (2) a leaked URL was never needed — bulk enumeration via a leaked API key or the console (mitigated by G10 secrets hygiene, not by delivery type); (3) a URL is guessed (already impractical).

## Options weighed

| | A — `authenticated` type + signed URLs | B — backend proxy / redirect per request | C — `private` type + expiring download URLs | D — leave as is, document |
|---|---|---|---|---|
| Mechanism | upload with `type: 'authenticated'`; every URL is generated by the SDK with `sign_url: true` (`s--…--` signature) | `GET /media/:id` checks ownership, then streams from Cloudinary (or 302s to a signed URL) | `type: 'private'`; originals via `private_download_url(expires_at)`; transformed derivatives need *strict transformations* | — |
| Stops a leaked URL | **No** — a signed URL has no expiry; it is a permanent capability for that asset + transformation. Revocation = delete the asset or rotate the API secret (kills every signed URL at once) | **Yes** — auth on every request; deactivation/purge cuts access instantly | Yes for *originals* (expiring); transformed delivery is either public or needs a per-transform signed URL (back to A) | No |
| Stops guessing / bulk delivery without credentials | Yes — Cloudinary refuses unsigned delivery of `authenticated` assets | Yes | Yes | ids are random already |
| Offline (SW CacheFirst on `res.cloudinary.com`) | **Works unchanged** — the signed URL is deterministic for (public_id, transformation), so the cache key is stable across renders | Needs the SW route moved to our origin; stream responses cache fine | Expiring URLs **break** CacheFirst — every new URL is a miss and a duplicate entry | unchanged |
| Cost / plan | free plan; one serializer chokepoint; one-off type change of existing assets | Railway egress + CPU on every image/video load; loses the CDN; a `<video>` needs range-request proxying; ~1 session | free plan, but strict transformations + two URL kinds — most complex | 0 |
| Emails / export | signed URLs work in mail and export (both are permanent anyway) | mail can't send cookies → still needs a signed URL path | expiring URLs in export are useless after a day | — |

**Rejected:** B for now — the strongest, and the right escalation, but it converts a CDN into a Railway hot path and reworks the offline story for a product with zero external users. C — fixes the wrong half (originals) and fights the transform pipeline. D — the privacy page makes a promise the current type does not keep, and A is cheap.

**Chosen: A**, with B recorded as the escalation and its trigger stated. What A honestly buys: no credential-less delivery of client media (enumeration off the table), a single revocation lever (rotate the secret) that today does not exist, and the URL-signing chokepoint that B would also need. What it does **not** buy: expiry of a URL that has already leaked — say so in SECURITY.md rather than imply it.

Cloudinary's expiring *token-based* delivery (cookie/URL tokens) would close that gap without a proxy — it is a paid-plan feature, listed under "Monitoring L5"-style triggers below rather than assumed.

## Design

1. **One chokepoint: `mediaDeliveryUrl(publicId, resourceType, transform?)`** in `cloudinary.service.ts` → `cloudinary.url(publicId, { type: 'authenticated', sign_url: true, secure: true, resource_type, transformation })`. The SDK computes the signature; nothing hand-builds URLs. Every serializer that returns client media calls it; the stored `cloudinary_url` stops being trusted (kept as a column for now — dropping it is a separate, later migration; nothing reads it after this).
2. **Upload with `type: 'authenticated'`** for client media only. `uploadBuffer()` gains an `access: 'public' | 'authenticated'` argument; exercise uploads pass `public`, snapshot + session-exercise uploads pass `authenticated`. No schema change.
3. **Existing assets: one-off type change** via `cloudinary.uploader.rename(publicId, publicId, { type: 'upload', to_type: 'authenticated', resource_type })` — a small script `apps/backend/src/scripts/migrate-media-to-authenticated.ts` reading both media tables, **dry-run by default** (lists what it would change, count by table), `--apply` to execute, idempotent (skips assets already `authenticated` — check via `api.resource`). Run once against prod by the designer after the code deploys (order: code first — the new serializer signs URLs for `authenticated` assets, and Cloudinary serves an `upload`-type asset through a signed authenticated URL? **No — see Unknowns 1**; the order is fixed there).
4. **Frontend: no change.** URLs still arrive ready to use. `getThumbnailUrl()` must never be applied to client media (it would break the signature) — add a one-line guard test so a future refactor cannot route progress photos through it.
5. **Service worker: no change.** CacheFirst keeps working because signed URLs are stable. Note in the SW comment that the signature is part of the cache key.
6. **CSP: no change** (`imgSrc`/media already allow `https:`).
7. **Export:** rows carry signed URLs (permanent, same posture as the data itself).
8. **Purge (A5):** `deleteByPrefix` must pass `type: 'authenticated'` for client folders, or the purge silently deletes nothing — test this; it is the kind of thing that "works" in a mocked test.
9. **Docs:** SECURITY.md G16 row ("signed, not expiring — rotate `CLOUDINARY_API_SECRET` to revoke everything"), `/privacy` wording check, DEFERRED_ITEMS entry for B/token-auth with triggers, CHANGELOG, runbook line for the one-off script.

## Tasks

1. **`mediaDeliveryUrl` + `uploadBuffer(access)`** *(low)* — chokepoint, upload flag, unit tests (URL contains `/authenticated/` and `s--` signature; public path unchanged; transform included in the signed part). Depends on: none.
2. **Serializers read-time signing** *(low)* — snapshot-media, session-exercise-media, progress-photos, session detail (form-check media), export. Route tests assert the URL is *derived*, not the stored column. Depends on: 1.
3. **Purge + delete paths pass the type** *(low)* — `deleteByPublicId` / `deleteByPrefix` for client media; test. Depends on: 1.
4. **One-off migration script** *(medium)* — dry-run default, `--apply`, idempotent, prints counts; unit-test the planner (which assets, which type) with the API mocked. Depends on: 1.
5. **Guard test** *(low)* — `getThumbnailUrl` never sees a client-media URL (source scan of `progress-photos/*` and the session panels). Depends on: none.
6. **Docs** *(low)*. Depends on: 1–4.

## Execution order
1 → 2 → 3 (one sitting; the media area loaded once) → 4 → 5 → 6. **Deploy order: code first, then run the script** *only if Unknown 1 resolves as expected*; otherwise the script goes first with a short window of broken images (see Unknowns). Designer runs the script (needs prod Cloudinary keys — never in a file).

## Unknowns — verify before building on them
1. **Does a signed `type: 'authenticated'` URL deliver an asset that is still `type: 'upload'`?** I believe **no** — delivery type is part of the asset's identity, so old assets will 404 under the new URL until renamed, and new assets would 404 under the old URL. That forces a sequence: (a) deploy code that signs *authenticated* URLs for assets marked authenticated and plain URLs for the rest — needs a per-row marker → either a `delivery_type` column (migration, 4-file rule) or "everything uploaded after `<timestamp>`"; or (b) accept a few minutes of broken client images between deploy and script. With one real user (the designer) and ~N assets, **(b) is the honest recommendation** — the column exists only to avoid a window nobody but you would see. Confirm the asset count first: `SELECT count(*) FROM snapshot_media` + `… FROM session_exercise_media`.
2. **`rename` with `to_type` on the free plan** — documented for all plans as far as I know; verify with one asset in dry-run → apply on a single id before the bulk run.
3. **Video delivery** — `<video src>` with range requests against an `authenticated` signed URL; expected to work (signature is per URL, not per request), but test one clip on the phone before calling it done.
4. **Signature scope** — whether the SDK includes the version segment in what it signs is irrelevant *as long as every URL comes from the SDK*; the guard in Task 5 is what keeps that true.

## Escalation triggers (recorded, not built)
- **Backend proxy (Option B):** a real incident of a leaked photo URL; or the first paying cohort; or a client-portal feature (magic links) that needs per-viewer access anyway.
- **Cloudinary token-based auth (expiring URLs, paid):** if a plan upgrade happens for other reasons (storage/bandwidth), take it — it closes the leaked-URL gap without the proxy.
- **Device-side cache:** the SW keeps client media for 30 days on any device that has viewed it; sign-out does not clear `cloudinary-media`. Worth clearing on sign-out (`caches.delete`) — small, separate item, add to `useSignOut`.
